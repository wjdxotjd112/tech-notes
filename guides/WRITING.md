# 작성 규칙

게시 절차는 [배포](DEPLOYMENT.md). 로컬 명령은 [운영](OPERATIONS.md). 그림·요약·강조·들여쓰기 등 화면 표현은 [문서 표현 표준](FORMATTING.md).

새 글은 편집형 상단 요약을 기본으로 사용. `summary_style: editorial`과 [재사용 코드](COMPONENTS.md) 적용. 기존 글은 일괄 변경하지 않음.

고정 목차와 종류별 글 템플릿은 사용하지 않음. 기준 글의 표현 방식을 적용하되, 새 글의 목적·자료·독자에게 필요한 설명에 맞춰 구성.

## 자동 시작

AI-Setup의 `skillnotes-publish`를 설치한 환경에서는 다음처럼 요청. 매번 규칙 파일이나 게시 명령을 지정할 필요 없음.

```text
이 내용을 블로그에 정리해줘.
```

자료 확인 → 분류·제목·구성·공개 범위 제안 → 사용자 승인 → 작성·검증·게시 순서. 초안만·검토만이면 게시 제외.

다른 workspace에서도 동작하도록 [AI-Setup 설치·검증](https://github.com/wjdxotjd112/AI-Setup/blob/main/docs/skillnotes.md)을 먼저 적용. 설치 전인 도구는 저장소의 `AGENTS.md`를 읽도록 지정. 설치 파일 확인과 새 세션의 실제 인식 확인은 별개.

## 문체

설명은 자연스러운 평서문, 관측값·환경·절차는 짧은 개조식과 목록을 섞어 작성. `~다`, `~했다`, `~이다`, `~한다` 종결 허용. `~습니다`, `~합니다`, `~했습니다`, `~세요` 같은 존대형은 사용하지 않음. 상단 요약과 본문에 같은 기준 적용.

AI가 쓴 듯한 인상을 줄이기 위해 종결어를 금지하거나 문장을 명사로 억지로 자르지 않음. 주체와 동작, 조건과 인과관계를 먼저 분명히 쓰고 문장 길이·표현 방식은 내용에 맞게 조절. 평서문과 개조식의 비율이나 순서를 기계적으로 맞추지 않음.

- 원인·이유·판단의 연결은 완결된 문장으로 설명. `~했고`, `~때문에`, `~하지만` 등 연결 표현은 실제 관계에 맞게 사용.
- 버전·수치·설정값·짧은 확인 결과는 표·목록·간결한 구절로 전달.
- 모든 문장을 `확인`, `발생`, `필요`, `~했음` 또는 `~다` 하나로 반복 종결하지 않음.
- 과장, 상투적인 도입·마무리, 같은 결론의 반복, 불필요한 독자 호명은 피함. 용어를 바꿔 쓰려고 실제 기술 의미를 흐리지 않음.
- 이유, 조건, 부정, 주의, 미확인은 남김. 작성 과정을 설명하는 메모를 본문에 넣지 않음.

예: `Controller별로 호출해 보니 문제 노드에서만 지연이 나타났다.` 다음에 대상·수치 표를 배치하고, `직접 호출에서도 느려 HAProxy 이후의 처리 경로를 추적했다.`처럼 다음 판단 연결.

명령, 코드, 로그, 인용은 문체를 바꾸지 않음.

## 처음 읽는 독자를 위한 설명

- 환경에서 서비스 역할·요청 흐름·프로세스 구성을 먼저 설명. worker·PID·스키마 등 용어는 처음 등장할 때 짧게 풀이.
- 분석은 의심한 이유 → 확인 방법 → 관측 결과 → 다음 판단으로 연결. 도구 이름과 결과만 나열하지 않음.
- 명령은 확인 목적·주요 옵션·출력 읽는 방법을 함께 작성. 실행 주의는 warning 박스로 구분.
- 요약은 전문용어와 숫자만 압축하지 않고 어떤 문제를 어떻게 해결했는지 먼저 설명. 수치는 무엇을 센 값인지 정의한 뒤 사용.
- 검증은 시험 방식과 횟수를 선택한 이유, 기대 동작, 결과 해석을 포함. 처음 보는 독자에게 불필요한 작성 메모·익명화 안내는 본문에 넣지 않고 실제 자료는 익명화.

## 근거

직접 실행, 사용자 제공 결과, 공식 문서, 가설을 구분한다. 실행 결과와 기대 결과를 구분한다. 실행하지 않은 작업을 완료로 쓰지 않는다. 없는 수치나 로그를 채우지 않는다. 부족한 곳은 `[확인 필요]`. 버전 의존 설명은 대상 버전과 공식 문서 링크를 붙인다. 일부 증거로 다른 원인을 모두 배제하지 않는다. 문서만 보고 쓴 글은 구축·검증 기록과 구분한다.

## 메타데이터

`docs/` 아래 `.md` 중 front matter에 `category`가 있으면 게시글이다. `docs/index.md`와 `category`가 없는 일반 페이지는 게시글이 아니다. `sample: true`는 예시 표시일 뿐, 목록에서 빼지 않는다. `draft` 속성은 없다.

| 항목 | 필수 | 자료형 | 의미 |
| --- | --- | --- | --- |
| `title` | 예 | 문자열 | 글 제목 |
| `summary` | 예 | 문자열 | 목록·글 상단 요약 |
| `summary_style` | 새 글에 예 | `editorial` | 편집형 본문 요약 스타일. 기존 글은 미지정 허용 |
| `date` | 예 | `YYYY-MM-DD` | 기록 기준일. 한국 날짜. 시간 없음. 홈은 이 값으로 최신이 위 |
| `category` | 예 | 아래 다섯 값 중 하나 | 화면 분류 |
| `tags` | 예 | 문자열 목록 | 기술 주제. 기존 표기 재사용 |
| `featured` | 아니오 | `true` / `false` | 대표 글. 한 글만. 기존 값을 임의로 바꾸지 않음 |
| `sample` | 아니오 | `true` / `false` | 예시 표시. 게시 제외 아님 |
| `figure_label` | 아니오 | 문자열 | 기존 화면용 라벨 |
| `figure_lines` | 아니오 | 목록 | 기존 화면용 줄 |
| `spotlight` | 아니오 | `true` / `false` | 기존 화면용 표시 |
| `spotlight_note` | 아니오 | 문자열 | 기존 화면용 짧은 설명 |

```yaml
title: "확인한 내용의 제목"
summary: "목록에 보일 짧은 요약"
summary_style: editorial
date: 2026-10-07
category: 트러블슈팅
tags:
  - Linux
```

`category`: `트러블슈팅`, `구축설계`, `자동화 CI/CD`, `성능 튜닝`, `개념`.

이미 쓰는 태그: `Linux`, `Observability`, `Network`, `OpenStack`, `Automation`, `가이드`. OpenTofu·VMware 자동화와 CI/CD 주제는 `Automation`으로 묶는다. 같은 뜻의 새 표기를 만들지 않는다.

## 경로

새 글 파일명: `docs/<폴더>/YYYY-MM-DD-짧은-이름.md`. 파일명의 날짜와 `date`를 맞춘다. 이미 공개된 글의 경로와 주소는 바꾸지 않는다.

| 폴더 | category |
| --- | --- |
| `docs/troubleshooting/` | 트러블슈팅 |
| `docs/design/`, `docs/labs/`, `docs/cheatsheets/` | 구축설계 |
| `docs/automation/` | 자동화 CI/CD |
| `docs/performance/` | 성능 튜닝 |
| `docs/concepts/` | 개념 |

폴더는 파일 정리용. 화면 분류는 `category`. 주소는 파일 경로. 사이트는 `/tech-notes/` 아래다.

이미지는 `docs/assets/`에 두고 글에서 상대 경로로 연결한다.

```markdown
![설명](../assets/example.png)
```

`guides/`, `drafts/`는 게시글 목록에 넣지 않는다. `drafts/`는 Git에 올리지 않는다.

## 종류

분류는 글의 주제를 구분하기 위한 값. 아래 질문은 설명할 내용을 고르는 기준이며, 목차 이름이나 절 순서를 강제하지 않음.

| 분류 | 독자가 이해해야 할 핵심 |
| --- | --- |
| 트러블슈팅 | 어떤 증상이 있었고, 무슨 근거로 원인을 좁혀 조치했는지 |
| 구축설계 | 왜 해당 구성을 선택했고 어떻게 구축·동작 확인했는지 |
| 자동화 CI/CD | 무엇을 입력받아 어떤 결과를 만들며 실패·재실행을 어떻게 처리하는지 |
| 성능 튜닝 | 무엇을 변경했고 같은 조건의 측정에서 어떤 차이가 있었는지 |
| 개념 | 기술의 역할·동작 원리·핵심 용어와 학습 예제가 어떻게 이어지는지 |

짧은 실험이나 개념 설명에는 필요한 내용만 작성. 항목을 맞추기 위한 빈 절·미실행 결과·반복 설명 추가 금지.

## 명령과 그림

코드·그림은 [문서 표현 표준](FORMATTING.md)과 그 문서가 연결한 실제 기준 글을 확인. 기존 구성 요소의 마크업·CSS를 재사용하고, 내용과 배치는 설명 대상에 맞게 작성. 고정 양식 파일을 복사하는 절차는 없음.

실행 위치, 대상, 바꿀 값, 목적을 적는다. 재시작·삭제·설정 변경은 영향과 주의를 적는다. 코드 펜스에 언어를 붙인다. 글 때문에 운영 시스템에 명령을 실행하지 않는다. 표와 그림은 이해가 필요할 때만. 외부 문서는 필요한 부분만 정리하고 출처를 연결한다.

## 공개

고객사, 내부 호스트, 내부 주소, 계정은 익명화. 토큰·비밀번호·개인키는 본문, 로그, 이미지, 주석, 커밋에 넣지 않는다. 작성자가 공개를 허용한 프로필은 예외. 문서용 IP는 `192.0.2.0/24`, `198.51.100.0/24`, `203.0.113.0/24`만. 공개 범위가 불명확하면 게시 전에 필요한 부분만 묻는다.

입력은 대화, 로그, Markdown, 메모, Notion, 외부 문서. 준 자료와 지정한 범위만 읽는다. Notion 전체와 Confluence는 가져오지 않는다.

## 검사 밖

`scripts/check_posts.py`와 `mkdocs build --strict`는 메타데이터, 날짜, 분류, `featured` 중복, 자리표시자, 링크·이미지 경로, 명확한 비밀 패턴, 빌드를 본다. 편집형 요약의 선언·필수 구조도 검사하지만 문체, 기술 판단, 이미지 속 민감정보는 별도 검토. 빌드 성공은 사실 검증이 아니다.
