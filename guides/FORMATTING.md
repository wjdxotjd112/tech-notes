# SkillNotes 문서 표현 표준

표현 기준은 [OpenStack API 지연 — attrs linecache 누적과 백포트](https://wjdxotjd112.github.io/tech-notes/troubleshooting/2026-10-07-openstack-attrs-linecache/). 함께 확인할 파일은 [기준 글 원문](../docs/troubleshooting/2026-10-07-openstack-attrs-linecache.md), [공통 스타일](../docs/stylesheets/fieldnotes.css), [MkDocs 설정](../mkdocs.yml).

**새 글에서 맞출 것은 읽는 방식과 시각 표현. 기준 글의 목차·절 개수·주제·수치를 그대로 따를 필요 없음.** 장애 분석, 구축, 자동화, 실험 등 글의 목적에 따라 설명 순서와 필요한 요소 선택.

메타데이터·문체·근거·공개 범위는 [작성 규칙](WRITING.md), 게시 절차는 [배포](DEPLOYMENT.md) 참고. 별도 글 템플릿은 사용하지 않음.

## 1. 기준 글을 활용하는 방법

먼저 자료에서 독자가 알아야 할 목적, 중요한 사실, 판단 근거, 결과를 파악. 내용을 구성한 뒤 각 설명에 맞는 시각 요소 선택.

- 같은 문체·글꼴·색상 의미·여백·코드박스 유지.
- 기준 글의 HTML/CSS 구성 요소는 필요한 부분만 재사용. 전체 글이나 목차를 복사하지 않음.
- 제목은 새 글의 실제 내용으로 작성. 기준 글의 여섯 절이나 “원인 분석”·“해결 방안”을 모든 글에 강제하지 않음.
- 설치 기록에는 설치 이유와 확인 방법, 실험에는 가설과 측정 조건 등 독자가 필요한 내용 배치.
- 정보가 없는 부분은 만들지 않음. 표현을 통일하기 위해 서로 다른 환경의 버전이나 관측값을 같은 값으로 바꾸지 않음.

## 2. 글의 시각적 계층과 목차

큰 주제는 번호가 있는 `##` 제목으로 구분. 한 절은 독자의 질문 하나나 작업 흐름 하나를 설명할 정도로 묶고, 절 개수는 내용에 맞게 결정.

세부 설명마다 `###`를 추가하면 오른쪽 목차가 길어지므로, 큰 절 안의 세부 내용은 굵은 문단 제목이나 토글로 구분. 순서가 있으면 `3-1.` 같은 하위 번호 사용. 번호는 해당 글의 실제 상위 절에 맞춤.

서로 밀접한 원리와 분석은 같은 절 안에, 코드 변경과 그 변경을 검증한 결과도 읽는 흐름에 맞춰 함께 배치 가능. 단순히 제목 수를 맞추기 위해 합치거나 분리하지 않음.

큰 주제 전환에는 Markdown `---` 구분선 사용. 문단마다 구분선을 넣거나 같은 내용을 제목·요약·결론에서 반복하지 않음.

## 3. 최상단 핵심 요약

긴 기술 글의 도입에는 기준 글의 `incident-summary` 영역 사용. 남색 제목 영역과 구분선이 있는 카드 영역으로 중요한 내용을 먼저 전달.

- 제목 영역: 글에서 다루는 문제나 목적을 구체적으로 표현.
- 카드: 글의 핵심 질문에 대한 짧은 답. 기준 글의 “증상·원인·해결·검증”은 장애 기록용 사례.
- 구축 글은 “목적·구성·선택 이유·확인 결과”처럼 내용에 맞는 이름 사용 가능. 카드 개수를 채우기 위한 설명은 추가하지 않음.
- 카드 하나는 보통 1~2문장. 핵심 수치나 판단만 굵게 표시.
- 낯선 함수명·캐시 번호만 압축해서 적지 않음. 어떤 문제가 있었고 무엇이 달라졌는지 평이한 표현으로 설명.
- 검증 완료, 개선 효과, 운영 반영 여부는 실제 근거 범위만 표현. 시험 성공을 운영 전체 성능 개선으로 확대하지 않음.

데스크톱은 두 열, 모바일은 한 열로 표시. `incident-summary-header`, `incident-summary-grid`, `summary-card` 등 현재 클래스와 구조 유지. 요약 영역의 제목을 새 `##`로 만들어 목차에 추가하지 않음.

## 4. 들여쓰기와 설명 묶기

하위 제목 아래 설명은 `section-body`로 묶어 **실제 렌더링 화면에서 제목보다 안쪽에 배치**. 글의 원문에 공백만 넣는 방식은 사용하지 않음.

- 하위 제목은 `subsection-title`로 구분.
- 본문, 목록, 코드, 표를 설명 단위로 같은 들여쓰기 영역에 배치.
- 원인·이유·확인 방법 같은 병렬 내용은 짧은 목록으로 분리.
- 의미가 없는 다중 들여쓰기는 피함. 하위 설명을 계속 중첩해 본문 폭을 좁히지 않음.
- 모바일에서도 제목과 본문의 시작 위치 차이가 보여야 하고, 코드·표 때문에 페이지 전체가 옆으로 넘치면 안 됨.

현재 공통 스타일의 본문 들여쓰기는 데스크톱 56px, 모바일 28px. 글마다 별도의 인라인 여백을 만드는 대신 기존 클래스를 사용. 수치는 스타일 조정 시 바뀔 수 있으므로 최종 판단은 실제 화면 기준.

## 5. 토글로 상세 내용 정리

질문이나 확인 항목은 보이게 두고, 그 아래 긴 과정은 토글로 접음. 독자는 제목만 훑고 필요한 설명을 펼칠 수 있어야 함.

기준 글의 `details.analysis-toggle`과 `summary`는 질문별 분석에 사용. 펼친 내용에는 의심한 이유, 확인 방법, 결과, 판단을 자연스럽게 연결. 이 네 단어를 모든 문단에 의무적으로 붙일 필요는 없음.

진단 명령·긴 출력·수동 검증 등 보조 자료는 `??? note` 사용 가능. 핵심 결론, 결정적인 결과, 실행 전 반드시 읽어야 할 주의를 접힌 자료에만 숨기지 않음.

- 토글 제목만으로 확인 대상이 드러나게 작성.
- 펼친 본문은 제목보다 들여쓰기.
- 원형 장식이나 임의 아이콘을 추가하지 않고 기존 펼침 화살표 사용.
- 단순한 한두 문장까지 모두 접거나 토글 안에 토글을 깊게 중첩하지 않음.
- 클릭·키보드로 열고 닫을 수 있는지, 코드 복사와 모바일 줄바꿈이 정상인지 확인.

## 6. 강조와 색상

색상은 정보의 역할을 구분하는 데 사용. 같은 역할에는 같은 표현을 사용하고, 색만으로 의미를 전달하지 않음.

| 내용 | 표현 | 작성 기준 |
| --- | --- | --- |
| 글의 핵심 요약 | 남색 제목 + 흰색 카드 | 목적·결과를 짧게 먼저 전달 |
| 장애 원인 결론 | `!!! danger`의 붉은 박스 | 제목에 “결론 — …”와 실제 원인 표시 |
| 핵심 원리·수정 효과·확인 기준 | `!!! tip`의 녹색 박스 | 독자가 기억할 한 가지 판단 |
| 실행 영향·적용 조건 | `!!! warning`의 주황색 박스 | 명령이나 조치 전에 필요한 주의 |
| 일반 보충 설명 | `!!! note` | 본문으로 쓰기 어려운 짧은 보충 |

붉은 결론 박스에는 원인과 그 원인을 뒷받침하는 근거를 짧게 작성. 확인이 끝나지 않은 가설을 확정된 결론처럼 표시하지 않음. 장애 원인이 없는 구축·개념 글에 붉은 박스를 의무적으로 넣지 않음.

박스에 들어간 내용은 주변 문단에서 그대로 반복하지 않음. 일반 설명 전체를 박스로 감싸거나, 모든 문장을 굵게·색상으로 강조하지 않음.

중요한 코드 한 줄은 `hl_lines`로 직접 강조. “두 번째 줄이 핵심” 같은 설명이 있으면 독자가 해당 줄을 바로 찾을 수 있게 표시.

## 7. 그림을 선택하는 기준

그림은 구성 요소의 관계나 처리 순서를 설명하는 용도. 단순한 한 가지 사실이나 이미 명확한 짧은 목록에는 추가하지 않음.

| 설명 대상 | 기본 표현 |
| --- | --- |
| 짧은 처리 순서 | 기존 `figure.flow` |
| 여러 노드·분기·요청 경로 | SVG 구성도 |
| 버전·조건·전후 수치 | 표 |
| 실제 UI·로그 화면 | 필요한 부분의 캡처 |
| 긴 코드·명령 | 그림이 아닌 텍스트 코드박스 |

구성도는 “무엇이 어디에 있고 어떻게 연결되는지”, 처리 흐름도는 “어떤 요청이 어떤 순서로 처리되는지” 설명. 한 그림에 모든 관계와 상세 코드를 몰아넣지 않음.

### 구성도와 요청 흐름

실제 참고 자산은 [Controller 구성도](../docs/assets/openstack-attrs-linecache/controller-topology.svg)와 [요청 흐름도](../docs/assets/openstack-attrs-linecache/token-request-flow.svg). 이 자산의 도형·선·글자 표현을 참고하고, 노드·관계는 새 글의 환경에 맞게 작성.

- 노드 하나에는 구성 요소나 처리 역할 하나를 짧게 표시.
- 요청, 응답, 처리 순서 중 화살표가 나타내는 의미를 일관되게 유지.
- 단방향·양방향·병렬 분기를 실제 관계에 맞춰 연결. 확인하지 않은 통신 경로는 사실처럼 추가하지 않음.
- 일반 환경 구성에는 정상·장애 판정을 섞지 않음. 문제 지점은 원인 분석용 그림에서만 필요한 경우 표시.
- 문제 지점을 색으로 표시하면 “지연” 같은 텍스트도 함께 사용.
- 관계가 복잡하면 구성도와 처리 흐름도를 분리하거나 여러 작은 그림으로 나눔.
- 그림 속 긴 문장은 본문으로 이동. 노드와 선이 겹치거나 글자가 상자 밖으로 나오지 않도록 확인.

### 크기·글자·파일

기준 글의 구성도는 `architecture-diagram`으로 본문 최대 폭 320px 표시. 관련 그림 두 개는 `environment-grid`에서 데스크톱 가로 배치, 모바일 세로 배치. 이 크기는 간단한 구성도의 출발점이며, 복잡한 그림까지 무조건 줄이는 규칙은 아님.

렌더링된 화면에서 한글과 라벨이 읽혀야 함. 글자가 작으면 내용 축약·그림 분리·표시 폭 조정 중 필요한 방법 선택. SVG 원본 링크도 연결해 확대 가능하게 구성.

| 요소 | 현재 사이트 기준 |
| --- | --- |
| 본문·노드 글자 | Pretendard 계열 + 한글 시스템 글꼴 대체, `#1e293b` |
| 도형 | 흰색 배경, 남색 `#0b1f3a` 윤곽 |
| 그림 바탕 | 흰색 또는 옅은 회색·파랑 |
| 연결선 | 파랑 `#2563eb`, 방향이 명확한 화살표 |
| 보조 설명 | `#3d4d63` |
| 문제 지점 | 필요한 경우 주황색과 텍스트 병기 |

자산은 `docs/assets/<글-slug>/` 아래 보관. SVG에는 `viewBox`, 제목·설명, 여백을 포함하고 글에서는 의미 있는 대체텍스트 사용. 수정 가능한 SVG 원본 유지.

현재 사이트에는 Mermaid 런타임이 없음. Mermaid로 작성하려면 `.mmd`와 렌더링한 `.svg`를 함께 보관하고 본문에 SVG 연결. 코드 펜스만 넣고 그림이 표시된다고 가정하지 않음.

“그림 1”, “클릭하면 확대”, “분석 대상의 개념도” 같은 설명은 자동으로 붙이지 않음. 제목·그림만으로 이해되지 않는 선의 의미나 범위가 있을 때만 캡션 추가.

## 8. 코드와 명령

Markdown 코드 펜스와 현재 사이트의 코드박스 사용. 밝은 회색 배경, JetBrains Mono, 얇은 테두리, 복사 버튼 유지. 별도의 검은 박스·스크린샷 코드·임의 `pre` 스타일 추가는 피함.

| 내용 | 언어 지정 |
| --- | --- |
| 실행 명령 | `bash` |
| 출력·로그 | `text` |
| 설정 | `yaml`, `json`, `ini`, `toml` 등 실제 형식 |
| 프로그램 | `python`, `javascript` 등 실제 언어 |
| 수정 비교 | `diff` |

명령 앞에는 목적과 필요한 실행 위치·대상·교체할 값을 설명. 처음 보는 독자가 “왜 이 명령을 실행하는지” 이해할 정도로 작성. 결과 뒤에는 무엇을 읽어야 하는지 짧게 해석.

명령과 출력은 별도 박스로 구분. 명령에는 `root@host`, `$` 같은 프롬프트를 넣지 않고 복사 가능한 내용만 작성. 실제 출력과 예상 출력은 구분하고, 생략한 로그는 생략 여부 표시.

설명이 필요한 주요 옵션만 풀어 쓰고 매뉴얼 전체를 복제하지 않음. 파일 구분에는 `title`, 핵심 줄에는 `hl_lines` 활용. 코드박스 줄 번호와 실제 원본 파일 줄 번호를 혼동시키지 않음.

긴 줄은 코드박스 안에서 스크롤. 명령을 줄바꿈할 때는 실제 실행 구문을 유지. 수동 입력이 필요한 환경이면 긴 스크립트보다 짧은 확인 명령 우선.

## 9. 코드 변경과 결과 비교

수정 내용을 설명할 때는 실제 변경 파일과 GitHub diff 링크 연결. 원본 파일을 추가한 커밋과 해당 파일을 수정한 커밋이 있어야 원본·수정 비교가 의미 있게 표시됨.

새 패치 파일 전체가 초록색으로 표시되는 화면을 소스의 before/after 비교처럼 안내하지 않음. 패치 다운로드는 별도 보조 링크로 제공.

기준 글의 [실제 코드 변경 커밋](https://github.com/wjdxotjd112/tech-notes/commit/93fe7d8ee88b13328e773f69ed50f991866f0542)은 비교 방식의 사례. 새 글에는 그 글의 실제 변경 커밋 연결.

전후 수치는 표로 비교하되 측정 대상·단위·조건부터 정의. “20개 → 2개”만 적지 않고 무엇을 센 값인지, 어떤 반복 작업에서 나온 값인지 먼저 설명.

실행 성공, 기능 검증, 성능 개선, 장기 안정성은 서로 다른 결과. 확인한 범위에 맞게 결론 작성.

## 10. 환경 표와 용어

환경 설명이 필요한 글은 OS·제품·관련 패키지 버전 등 분석이나 재현에 필요한 항목을 표로 제시. 제공된 자료 중 관련 있는 값만 사용하고 관련 없는 정보를 표에 늘어놓지 않음.

운영과 별도 검증 환경이 다르면 결과를 이해하는 데 필요한 차이를 표시. 표현의 통일은 실제 값의 통일을 뜻하지 않음.

worker·스키마·캐시 등 낯선 용어는 처음 필요한 위치에서 짧게 설명. 용어를 설명하기 위해 소제목을 계속 추가하지 않고 본문이나 목록에 자연스럽게 배치.

“정상 노드”·“문제 노드”처럼 역할이 드러나는 이름을 일관되게 사용. 여러 노드가 꼭 필요할 때만 A/B/C 등 식별자 병기.

숫자나 ID에 대한 설명은 해당 관측값 옆에 배치. 번호의 의미를 여러 문단 뒤에 별도 박스로 갑자기 등장시키지 않음.

## 11. 현재 구성 요소를 재사용하는 위치

완성된 [기준 글 원문](../docs/troubleshooting/2026-10-07-openstack-attrs-linecache.md)에서 필요한 구성 요소를 찾아 사용. 별도 복사 양식이나 고정 목차 파일은 없음.

| 구성 요소 | 마크업·클래스 | 사용 목적 |
| --- | --- | --- |
| 상단 요약 | `section.incident-summary` | 글의 핵심을 카드로 전달 |
| 세부 제목 | `p.subsection-title` | 목차를 늘리지 않는 하위 구분 |
| 들여쓴 설명 | `div.section-body` + `markdown="1"` | 본문·코드·표를 한 설명 단위로 묶기 |
| 질문별 토글 | `details.analysis-toggle` + `summary` | 긴 조사·비교 과정을 선택해서 읽기 |
| 보조 자료 토글 | `??? note` | 상세 명령·출력·수동 절차 |
| 단순 흐름 | `figure.flow` | 짧은 단계의 선후 관계 |
| 구성도 이미지 | `architecture-diagram` | SVG 크기와 배치 통일 |
| 그림 묶음 | `environment-grid` | PC 두 열·모바일 한 열 |
| 결론·핵심·주의 | `!!! danger`·`tip`·`warning` | 정보 역할에 맞는 강조 |

새 글은 기존 클래스를 사용. 같은 용도의 CSS를 글마다 복제하지 않음. 새 시각 요소가 필요하면 현재 구현으로 표현 가능한지 먼저 확인하고 꼭 필요한 범위만 추가.

## 12. 작성 후 확인

[배포 절차](DEPLOYMENT.md)의 문서 검사와 strict 빌드 후, 변경한 표현에 맞춰 실제 화면 확인.

- 목차가 큰 주제만 보여주고, 하위 제목 아래 본문·표·코드가 실제로 들여써지는지.
- 요약이 처음 보는 독자에게 문제나 목적을 설명하는지, 숫자·약어만 나열하지 않았는지.
- 토글을 열고 닫을 수 있고 중요한 결론이 접힌 내용에만 숨지 않는지.
- 그림의 한글·화살표·노드가 잘리거나 겹치지 않고, 모바일에서도 읽을 수 있는지.
- 코드 복사 내용이 실행할 명령과 일치하고, 가로 스크롤이 해당 코드·표 안에 머무는지.
- 결론의 색상과 문구가 실제 근거 수준에 맞는지.
- 최종 공개 URL에서 변경 내용이 반영됐는지.

단순 문구 변경이면 관련 문구·링크 확인, 그림·레이아웃 변경이면 PC·모바일 렌더링 확인. 통과한 검사를 이유 없이 반복하거나 글의 범위를 벗어난 시험을 추가하지 않음.
